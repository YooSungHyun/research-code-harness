# research-code-harness

Claude Code CLI에서 요청 한 줄을 던지면, 요청의 뜻을 따져보고 → 조사 → 계획 → 한 항목씩 작업 →
실제 검증 → 보고까지 알아서 끝내는 하네스입니다. 만들고 싶은 프로그램, 연구하고 싶은 논문 주제,
기존 코드에 붙일 기능을 같은 흐름으로 처리합니다.

## 무엇을 정확하다고 보는가

결과가 **요청한 사람이 뜻한 바로 그것**이면 정확한 것입니다. 기준은 사용자의 원문입니다.
다만 원문은 대개 짧고 부정확할 수 있어서, 일을 시작하기 전에 이렇게 합니다.

1. 에이전트 셋이 서로 보지 않고 각자 다른 관점으로 요청을 읽습니다
   (글자 그대로 / 요청한 목적 / 잘못 읽힐 수 있는 지점).
2. 해석이 갈리는 곳이 곧 요청이 애매한 곳입니다. 맥락상 분명하면 하나를 택하고,
   싸게 둘 다 만족시킬 수 있으면 둘 다 하고, 결과가 크게 달라지는데 알 수 없으면 사용자에게 묻습니다.
3. 결과가 맞아야 하는 **경우의 수**를 정리합니다. 이후 작업과 검증은 이 경우들을 대상으로 합니다.
4. 계획이 나온 뒤와 결과가 나온 뒤에, 의도 점검 에이전트가 요약이 아닌 **원문**을 들고
   빠진 것 / 요청하지 않았는데 들어간 것 / 다르게 읽은 것 / 제대로 검증되지 않은 경우를 찾습니다.

요청을 좁게 읽어 당연한 기대를 놓치는 것과, 넓게 읽어 시키지 않은 것을 만드는 것 모두 실패로 봅니다.

## 한 세션이 직접 일합니다

조사, 계획, 구현, 실행 확인은 요청을 읽은 세션 하나가 처음부터 끝까지 직접 합니다.
역할별로 에이전트를 나누면 넘길 때마다 요청의 뜻이 조금씩 빠지기 때문입니다.
다른 에이전트는 "일하지 않은 쪽의 눈"이 필요한 곳과, 서로 독립이라 병렬로 돌리면 빨라지는 곳에 씁니다.

| 에이전트 | 언제 | 왜 따로 |
|---|---|---|
| `intent-checker` | 시작할 때 셋(관점별 해석), 계획 뒤, 결과 뒤 | 자기 해석의 사각은 자기가 볼 수 없어서 |
| `reviewer` | 체크리스트의 리뷰 항목: 바뀐 것을 읽고, 돌려보고, 사용자처럼 써봄(웹 UI는 실제 브라우저) | 만든 쪽은 자기 가정을 공유해서 |
| `scout` | 조사할 독립된 질문이 여럿일 때, 질문당 하나씩 동시에 | 병렬로 돌리면 가장 오래 걸리는 질문 하나만큼만 걸려서 |

## 계획은 살아 있는 체크리스트

`projects/<이름>/.harness/PLAN.md`의 체크리스트가 작업의 실제 상태입니다.

```markdown
## Checklist

- [x] S1 서버 뼈대와 첫 테스트
  - cases: C1, C2
  - check: `uv run pytest -q`
  - done: 2026-11-27 3 passed
- [ ] S2 할 일 추가
  - cases: C6, C7
  - check: `uv run pytest tests/test_add.py -q`
- [ ] V2 Independent review and real use (reviewer)

## Changes
- 2026-11-27 added S2a: 리뷰에서 공백 입력이 추가되는 문제 발견
```

- **하나씩**: 맨 위의 열린 항목만 작업하고, 확인 명령이 실제로 통과하는 즉시 체크하고 커밋합니다.
  여러 개를 한꺼번에 체크하지 않습니다.
- **바뀝니다**: 항목이 끝날 때마다, 리뷰가 끝날 때마다 남은 목록을 다시 보고 추가·수정·삭제합니다.
  이유는 `Changes`에 남깁니다.
- **체크는 되돌릴 수 있습니다**: 나중 확인에서 끝난 항목이 틀렸거나 다시 해야 하면 체크를 풀고
  (`reopened:` 줄에 이유), 그 결과에 기대던 검증 항목의 체크도 같이 풉니다.
- **전부 체크돼야 끝**: 열린 항목이 남은 채 완료로 표시하면 훅이 세션 종료를 막습니다.

형식이 고정돼 있어서(`- [ ] <ID> <제목>` 한 줄 + 들여쓴 `key: value`) 파일만 보고도, 나중에 UI를 붙여서도
진행 상황을 따라갈 수 있습니다. `S`는 작업 항목, `V`는 검증 항목입니다.

## 기본 규칙

- 기존 코드가 있으면 먼저 직접 다 읽고, 기존 파이프라인과 충돌 없이 추가합니다.
- 실제로 돌려서 검증합니다. 웹 데모는 실제 브라우저에서 띄워 스크린샷으로 확인합니다.
- 시간은 제약이 아닙니다. 추측하지 않고 코드를 읽고, 명령을 돌리고, 문서를 확인합니다.
- 최종 보고에는 진행 중 **실제로 발생한 문제**만 적습니다.

## 사용법

```bash
cd research-code-harness
claude --permission-mode auto      # 무인 진행에는 auto 모드 권장
```

세션에서 만들거나 연구할 것을 말하면 됩니다. `/harness`를 붙여도 되고 그냥 말해도 됩니다.

```
/harness 논문 X의 방법을 구현해서 Y 데이터로 재현해줘
```

- 프로젝트 이름은 하네스가 정하고, 모든 작업은 `projects/<이름>/` 폴더 안에서 이뤄집니다.
- 질문은 시작할 때 한 번만 합니다(유형, 해석이 갈리는 지점, 승인이 필요한 플러그인).
  그 뒤로는 끝날 때까지 혼자 진행합니다.
- 이어서 하거나 상태를 볼 때: `/harness-resume [이름]`

세션을 열어두지 않고 헤드리스로 돌릴 때는 설정 두 가지가 필요합니다. 권한 모드가 없으면 승인이
필요한 명령이 모두 거부되고, 대기 제한을 풀지 않으면 백그라운드 에이전트가 10분을 넘길 때 세션이 끝납니다.

```bash
CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 claude -p "/harness --auto <요청>" --permission-mode auto
CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 claude -p "/harness-resume <이름>" --permission-mode auto   # 중간에 끊겼을 때
```

## 진행 흐름

```
understand → discover → plan → build → verify → report
```

| 단계 | 하는 일 | 남는 것 |
|---|---|---|
| understand | 유형 결정(연구/코드/혼합), 이름 짓고 uv 프로젝트 폴더 생성, 기존 코드 읽기, 요청 해석, 질문 1회, 도구 검토 | `CLAUDE.md`, `INTENT.md`, `TOOLING.md` |
| discover | 필요한 각도로, 요청 크기에 맞는 깊이로 조사하고 스스로 반박해 봄 | `analysis/`, `SYNTHESIS.md` |
| plan | 설계와 체크리스트 작성, 계획을 원문과 대조 | `PLAN.md` |
| build | 체크리스트의 작업 항목을 하나씩: 작업 → 실제 확인 → 체크 → 커밋 | 커밋, `ISSUES.md` |
| verify | 체크리스트 끝의 검증 항목: 전체 실행, 독립 리뷰와 실제 사용, 경우별 검증표, 결과를 원문과 대조 | `VERIFICATION.md`, `evidence/` |
| report | 보고서, 설치한 도구 제거, 배운 것 기록 | `REPORT.md` |

작업 유형에 따라 조사와 검증이 달라집니다.

| 유형 | 결과물 | 최종 검증 |
|---|---|---|
| `research` | 조사·분석 문서, 질문에 대한 답 | 주장 하나하나를 출처·결과 파일과 대조 |
| `code` | 동작하는 소프트웨어 | 전체 실행, 독립 리뷰, 실제 데모 |
| `hybrid` | 구현과 실험 결과 | 위 전부 |

기존 저장소에 기능을 추가할 때는 `harness/<이름>` 브랜치의 git worktree에서 작업하므로
원래 체크아웃은 건드리지 않습니다. 하네스 기록도 그 저장소에 들어가지 않습니다.

## 구성

```
CLAUDE.md                      # 모든 프로젝트에 적용되는 작업 규칙과 누적된 교훈
CLAUDE.local.md                # 이 머신에 대한 사실 (커밋하지 않음, 하네스가 관리)
.claude/
├── skills/harness/            # 진행 방식 + 단계별 가이드(phases/)
├── skills/harness-resume/     # 이어가기·상태 보기
├── skills/harness-browser/    # 브라우저 검증 방법 + Playwright 드라이버
├── agents/                    # intent-checker, reviewer, scout
├── hooks/harness_hook.py      # 자동 진행 훅 (유일한 스크립트)
└── settings.json              # 훅·권한
projects/<이름>/               # 프로젝트마다 독립된 uv 프로젝트 + git 저장소
├── CLAUDE.md                  # 이 프로젝트의 문맥: 요청 원문, 해석, 명령, 규칙
└── .harness/                  # INTENT, 조사, PLAN(체크리스트), 증거, 이슈, 보고서, STATUS
```

### CLAUDE.md를 쓰는 방식

- **프로젝트 `CLAUDE.md`**: 그 폴더에서 일하는 세션과 에이전트가 자동으로 읽습니다. 요청 원문과
  해석(`INTENT.md`를 가져옴), 통하는 명령, 코드 관례, 건드리면 안 되는 것을 담고 작업하면서 갱신합니다.
  끝날 때는 나중에 그 폴더를 여는 사람을 위한 문서로 정리합니다.
- **하네스 `CLAUDE.md`**: 작업 규칙. 프로젝트를 마칠 때 다른 프로젝트에도 통할 교훈이 있으면 한 줄씩 추가됩니다.
- **`CLAUDE.local.md`**: GPU 유무, 설치된 도구, 주의할 점 같은 머신 정보.

### 플러그인

시작할 때 이 작업에 추가 도구(플러그인, MCP 서버 등)가 필요한지 검토합니다. 대부분은 "필요 없음"입니다.
필요하면 이 저장소 범위(local)로 설치하고 `TOOLING.md`에 기록하며, 프로젝트가 끝나면 제거합니다.
원래 설치돼 있던 것은 건드리지 않습니다. 공식 마켓플레이스와 이미 등록해 둔 마켓플레이스 밖의 것은
설치 전에 물어봅니다. 설치한 것이 남아 있으면 훅이 세션 종료를 막고 제거하게 합니다.

세션 도중 설치한 플러그인은 그 세션에 바로 적용되지 않습니다. 설치한 경우 하네스가
`/reload-plugins` 입력을 한 번 요청합니다.

### 자동으로 계속 진행되는 원리

`projects/<이름>/.harness/STATUS.md` 첫 줄들(`status`, `session`, `phase`, `next`)과 `PLAN.md`의 체크리스트가 상태입니다.

- **Stop 훅**: 상태가 `running`이면 세션이 멈추려 할 때 `next`와 체크리스트 진행 상황을 들려 다시 일하게 합니다.
  사용자 결정이 필요한 `waiting`과 완료 `done`에서는 멈춥니다. 다만 열린 항목이나 설치한 도구가 남아 있으면
  `done`이어도 붙잡습니다. 변화 없이 세 번 연속 멈추면 놓아줍니다.
- **SessionStart 훅**: 세션 시작·재개·컨텍스트 압축 뒤에 진행 중인 프로젝트와 다음 할 일을 다시 알려줍니다.

### 브라우저 검증

`ego-browser`가 설치돼 있으면 그것으로, 없으면 내장 Playwright 드라이버로 실제 브라우저를 띄웁니다.
ego-browser(ego lite)는 macOS와 Windows만 지원하므로 Linux 서버에서는 Playwright(헤드리스 Chromium)가 쓰입니다.

## 요구 사항

- Claude Code CLI, `uv`, `git`, Python 3
- 브라우저 검증: `ego-browser`, 또는 Node.js(Playwright용 Chromium은 첫 실행 때 자동 설치)

## 권한

`.claude/settings.json`은 편집 자동 승인과 `uv`·`git` 조회 명령 허용을 기본으로 둡니다.
`git push`와 `sudo`는 항상 묻고, SSH 키와 자격 증명 파일 읽기는 막습니다.
